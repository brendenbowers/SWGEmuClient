Actor hierarchy

UE doesn't allow multi-inheriting actor classes, so ASWGCreature can't extend both a tangible base and ACharacter. Shared TANO fields move into a component instead of a common actor base:

AActor
└── ASWGItem — plain actor: props, resources, static items, weapons
    + USWGTangibleComponent

ACharacter
└── ASWGCreature — pawn: NPCs, player bodies
    + USWGTangibleComponent (same component type, composed in)
    + USWGMovementComponent : UCharacterMovementComponent
    + USWGHealthComponent, USWGSkillComponent, USWGEquipmentComponent,
      USWGCombatStateComponent, USWGGroupComponent, USWGPerformanceComponent
    + (if player-controlled) USWGQuestComponent, USWGExperienceComponent,
      USWGAbilityComponent, USWGVitalsComponent, USWGProfileComponent

AActor (new — building/static/installation branch, confirmed via Core3)
├── ASWGStaticProp — STAO, near-trivial: ObjectName/CustomName only
├── ASWGBuilding — BUIO, owns child cells
├── ASWGCell — TLCS, keyed by cellNumber not object id, spawned by owning Building
└── ASWGInstallation — INSO: USWGTangibleComponent + Active/SurplusPower/BasePowerRate
Why no shared interface needed for dispatch

The message router already knows the object's FourCC (CREO/TANO/PLAY/...) before it touches the actor, so the sequence of components to call for a given (FourCC, slot) pair is fixed at the call site — no virtual ApplyBaselineSlot() on the actor is needed. See Message dispatch model.

Message dispatch model

Baseline slots are one continuous byte stream shared across components — CreatureObjectMessage3 is literally TangibleObjectMessage3's bytes followed immediately by creature-specific bytes on the same packet cursor. So apply order matters and must be explicit per (FourCC, slot):

C++namespace SWGCreatureBaselineApply
{
    void ApplyBase3(AActor* Actor, FSWGPacket& Packet)
    {
        Actor->FindComponentByClass<USWGTangibleComponent>()->ApplyBase3(Packet);
        Actor->FindComponentByClass<USWGCombatStateComponent>()->ApplyBase3Tail(Packet);
    }
}

The subsystem's job shrinks to: spawn-on-Create, ID registry, and calling these free functions — no virtual dispatch on the actor needed, since the FourCC is already known at the call site.

C++ — subsystem routingif (FourCC == TEXT("CREO"))
{
    AActor* Actor = FindActor(Baseline->ObjectId);
    switch (Baseline->BaselineType)
    {
        case 1: SWGCreatureBaselineApply::ApplyBase1(Actor, Sub); break;
        case 3: SWGCreatureBaselineApply::ApplyBase3(Actor, Sub); break;
        case 4: SWGCreatureBaselineApply::ApplyBase4(Actor, Sub); break;
        case 6: SWGCreatureBaselineApply::ApplyBase6(Actor, Sub); break;
    }
}
Spawn timing

Spawn the actor immediately (hidden) on SceneCreateObjectByCrc instead of buffering into an intermediate struct. Baselines/deltas then apply straight onto live components. SceneEndBaselines just un-hides it. This removes the FSWGObjectRecord accumulator and the TOptional<FXxxBaseline> struct fields entirely — the components are the decoded state.

Delta application (confirmed field indices)

Wire shape, confirmed against Core3's DeltaMessage.h:29-160 and the per-type *ObjectDeltaMessageN.h headers: each entry in RawUpdates is [fieldIndex:uint16][value], one entry per server-side startUpdate() call. Field index restarts at 0 for every slot — CreatureObjectDeltaMessage6 uses 0x02–0x10 independently of CreatureObjectDeltaMessage3's 0x00–0x11 and ...4's 0x00–0x0C. This means our existing per-slot ApplyBaseX component methods get a same-slot ApplyDeltaBaseX(uint16 FieldIndex, FSWGPacket&) sibling — no new dispatch mechanism, just a switch(FieldIndex) mirroring baseline declaration order.

USWGObjectStoreSubsystem is a UGameInstanceSubsystem, so it survives level transitions — Deinitialize() only fires at game-instance shutdown, never on a plain level change. Per-object state machine

(unknown) ──SceneCreateObjectByCrc──▶ Pending ──first BaselinesMessage──▶ Spawned ──SceneEndBaselines──▶ Ready ──??? (gap)──▶ Destroyed
  • Pending — SceneCreateObjectByCrc received; no actor exists yet. Transform/CRC/hyperspacing held in a small PendingSpawns buffer keyed by ObjectId.
  • Spawned — first BaselinesMessage for that ObjectId arrived, its FourCC picked the actor class, the actor was spawned hidden at the buffered transform and registered. Every baseline slot after this (including this first one) dispatches straight to ApplyBaseX on the live actor's components.
  • Ready — SceneEndBaselines received: un-hide, enable collision, broadcast OnObjectReady(ObjectId).
  • Destroyed — gap, see below.

Phase A vs. Phase B

Phase A (this pass — messages only): every object is invisible for one extra round trip (its own Create, then its first Baseline) before its class is known and it can spawn. Correctness over latency for this first pass.

Phase B (later — once the CRC table from the earlier phase is wired in): resolve class immediately from Crc on SceneCreateObjectByCrc, spawn hidden right away, apply baselines onto an already-existing actor — removing the PendingSpawns buffering step entirely. Dispatch should key off the resolved template's outer FORM tag (SCOT/STOT/STAT/SBOT/SIOT/CCLT/...), not the CRC path prefix — see Template FORM types. The path prefix and template class don't always line up 1:1 (e.g. object/tangible/component and object/weapon are both "tangible-ish" paths but resolve to different FORM tags), and the FORM tag is authoritative since it's the actual class discriminator baked into the file.

Object ID registry

FindComponentByClass filters by type only — for "give me the actor for object ID X" you need your own index:

C++UCLASS()
class SWGEMU_API USWGObjectStoreSubsystem : public UGameInstanceSubsystem
{
    void RegisterActor(int64 ObjectId, AActor* Actor);
    void UnregisterActor(int64 ObjectId);
    AActor* FindActor(int64 ObjectId) const;

    template<typename T>
    T* FindComponent(int64 ObjectId) const
    {
        AActor* Actor = FindActor(ObjectId);
        return Actor ? Actor->FindComponentByClass<T>() : nullptr;
    }

    TMap<int64, TWeakObjectPtr<AActor>> ActorRegistry;
};

TWeakObjectPtr auto-nulls on actor destroy, so despawn cleanup is free even if UnregisterActor isn't called explicitly.

CRC table format

misc/object_template_crc_string_table.iff (found in data_other_00.tre, superseded by later patch archives — latest wins). Parsed with F:\Projects\Scripts\ParseCrcTable.ps1:

FORM CSTB
  FORM 0000
    DATA (4 bytes)   — record count, uint32 LE (15,792 in patch_14_00.tre)
    CRCT (count×4)   — array of uint32 CRCs, index-aligned with STRT
    STRT (count×4)   — array of uint32 offsets into STNG
    STNG (blob)     — concatenated null-terminated template path strings

Row i: CRC = CRCT[i], path = null-terminated string at STNG + STRT[i] (e.g. object/tangible/ship/components/droid_interface/...). This is the same CRC carried in SceneCreateObjectMessage::ObjectCrc — so a lookup at spawn time gives the template path before any baseline arrives.

Core3 server source survey

Terrain — confirmed zero network geometry

CmdStartScene.h:28: the server sends only a terrain file path string — "terrain/" + zoneName + ".trn" — plus spawn position/CRC/galactic time. No heightmap or mesh data crosses the wire. Terrain is a pure TRE-extraction task: pick the local .trn by name, no baseline/delta code involved at all.

Statics (STAO) — networked, not TRE-baked

StaticObject extends SceneObject (staticobject/StaticObject.idl:12) with a native sendBaselinesTo() (line 31). Wire baseline StaticObjectMessage3.h:14-22, FourCC 0x4F415453 ("STAO"): int(0), StringId(ObjectName), CustomName, int(0xFF). So every static prop gets its own SceneCreateObjectByCrc + a single lightweight baseline slot (3) — no condition/HAM/etc. This is the simplest baseline in the game; ASWGStaticProp can be a near-trivial actor.

Buildings (BUIO) & Cells (TLCS)

BuildingObject extends StructureObject (building/BuildingObject.idl:32), FourCC 0x4255494F ("BUIO") per BuildingObjectMessage3.h:14 / BuildingObjectMessage6.h:13.

Stale reference files

Both BuildingObjectMessage3.h and BuildingObjectMessage6.h are entirely commented out (dead/legacy code) — the live baseline construction path wasn't located in this pass. Treat these two files as historical reference for FourCC/field layout only; a follow-up grep in BuildingObjectImplementation.cpp is needed before implementing ASWGBuilding's baseline parser.

CellObject extends SceneObject (cell/CellObject.idl:18), FourCC 0x53434C54 → wire bytes read as ASCII "TLCS" (CellObjectMessage3.h:13, cross-checked against a captured packet in that file's comments). Cells are separate baseline objects, keyed by cellNumber (int, not object id) — CellObjectMessage3.h:21. BuildingObject.addCell()/getCell() (BuildingObject.idl:232,244) confirm cells are children enumerated by index, created via createCellObjects() (line 96) — i.e. a building spawns its own set of cell objects rather than cells being independently discovered.

Installations (INSO)

Extend StructureObject, but the baseline wraps TangibleObjectMessage3 directly — InstallationObjectMessage3.h:11,14, FourCC 0x494E534F ("INSO"). Base3 appends only 3 installation-specific fields after the full tangible payload (InstallationObjectMessage3.h:39-41): Active (byte), SurplusPower (float), BasePowerRate (float). No hopper/resource-contents fields in base3 — this means ASWGInstallation is just USWGTangibleComponent + 3 scalars, no new component needed.

Mesh rendering — runtime-only constraint

To actually render spawned objects (not just track them in the object graph), we need real geometry from the TRE archives. This can't be a build-time/offline conversion baked into the project — everything must be parsed from the user's own TRE files at runtime, never redistributed. So the target is an on-the-fly parser + converter, with a local (gitignored, per-machine) cache of the converted result to avoid re-parsing on every launch — never a cache of pre-converted assets shipped with the project.

Must work in a packaged/shipping build, not just PIE

Unreal's normal mesh build pipeline (MeshUtilities::BuildSkeletalMesh, FSkeletalMeshImportData) is editor-only and unavailable in a packaged game. For static, unskinned meshes this doesn't matter — UDynamicMeshComponent (Geometry Script's runtime mesh type, its own runtime module, not editor-only) is designed exactly for this: hand it vertex/normal/UV/triangle data and it renders in a shipping build with optional collision. (UProceduralMeshComponent is an older alternative that does the same job.)

Decision: bind-pose-only creatures/players for now, real animation deferred

Real bone-animated skeletal meshes need USkeletalMeshComponent, and there's no well-supported runtime-safe way to build one in a packaged build — it means hand-populating FSkeletalMeshLODRenderData/skin-weight buffers directly, bypassing the (editor-only) import pipeline entirely. Rather than take that on now, phase 1 renders .mgn creatures/players in their bind pose only — same UDynamicMeshComponent pipeline as static meshes, just baking the un-animated POSN/NORM vertex positions in directly, no skinning applied. No animation, IK, or Anim Blueprint support in this phase; that's a distinct, larger follow-up project once bind-pose rendering works end to end.

Materials are a separate problem from geometry either way: a .sht shader reference can't be compiled to HLSL at runtime, so the plan is pre-authored master material(s) in the project with texture-parameter slots, populated at runtime via UMaterialInstanceDynamic with textures decoded from the TRE's .dds files. Not yet started — geometry comes first.

Vertex layout — derived from stride, not a guessed bit table

The key simplification: we don't need to fully decode what every flag bit means — stride = DataSize / VertexCount is directly measurable, and only one bit matters for byte layout:

  • position (3×float, 12 bytes) — always present, offset 0
  • normal (3×float, 12 bytes) — always present, offset 12
  • color (packed RGBA8, 4 bytes) — present only if flags & 0x08, offset 24
  • UV channels (2×float each, 8 bytes) — count N = (stride - 24 - color) / 8

Confirmed across every real sample pulled: 0x1105→stride 32 (1 UV, no color), 0x110D→stride 36 (1 UV + color, isolates bit 0x08 exactly), 0xD205/0x015305→stride 48 (3 UV), 0x055405→stride 56 (4 UV). Positions land exactly on bounding-box corners, normals are unit-length cardinal vectors, UVs fall in sane ranges and correlate correctly between adjacent vertices.

No weld/reindex step needed

Unlike .mgn below, .msh stores one combined vertex per DATA entry and INDX is a single flat triangle-index buffer referencing those combined vertices directly — feeds straight into UProceduralMeshComponent::CreateMeshSection() with no OBJ-style per-attribute reindexing.

.mgn format (skeletal mesh) — confirmed

Different scheme from .msh: positions/normals are shared flat arrays across the whole mesh, and per-submesh indexing needs one extra indirection layer (decoded and verified via DecodeMgn.ps1 against real samples, including a full end-to-end vertex reconstruction check).

FORM SKMG > FORM 0004
  SKTM       — skeleton reference path (e.g. appearance/skeleton/all_b.skt)
  XFNM       — bone/transform names used by this mesh
  POSN       — shared position array (3×float per vertex)
  NORM       — shared normal array (3×float per vertex)
  TWHD / TWDT — per-vertex bone-weight count / (bone-index, weight) pairs, indexed by POSN index
  OZN / OZC   — named hit-location zones (chest, l_arm, r_foot, ...) for combat
  FORM PSDT   — one per shader submesh
    NAME       — shader reference
    PIDX       — [count:uint32][count × uint32 positionIndex] — corner-index → POSN index
    NIDX       — [count × uint32 normalIndex], no leading count (matches PIDX's) — corner-index → NORM index
    FORM TCSF > TCSD  — [count × (float U, float V)], directly corner-indexed, same count as PIDX/NIDX
    FORM PRIM > OITL  — [TriCount:uint32][TriCount × (uint16 flag, uint32 corner0, uint32 corner1, uint32 corner2)]
Parsing gotcha hit while decoding this

PIDX carries its own leading uint32 count prefix; NIDX does not (its count is implied to equal PIDX's). Missing this produced a bogus off-by-one entry-count mismatch and out-of-range index values that looked like a real format anomaly until the prefix was accounted for. Once corrected, PIDX/NIDX both range cleanly [0, POSN.Count-1].

Reconstructing a real vertex from a corner index c: Position = POSN[PIDX[c]], Normal = NORM[NIDX[c]], UV = TCSD[c] (UV needs no extra lookup — it's already 1:1 with the corner-index space). OITL's three corner fields per triangle reference these corner indices directly.

The file already did the "weld" for us

Originally assumed this format needed an OBJ-style re-indexing pass (separate per-attribute indices → explode into unique per-corner vertices → dedupe). In practice it's simpler: build one "corner vertex" array of exactly count entries (Vertex[c] = (POSN[PIDX[c]], NORM[NIDX[c]], TCSD[c])), and OITL's corner-index triples become the UE triangle index buffer unchanged — no further deduplication needed. Skinning (TWHD/TWDT) is looked up via the same PIDX[c] position index.

.trn format — procedural terrain generator (Core3-confirmed)

.trn is not a heightmap — confirmed via a real sample (terrain/character_farm.trn) and cross-referenced against Core3's own reference implementation at MMOCoreORB/src/terrain/ (TerrainGenerator.cpp, Layer.cpp, ProceduralTerrainAppearance.cpp, plus ~20 layer/affectors/* and 5 layer/boundaries/* classes). It's a procedural node graph — shader/flora/river/environment "groups" plus a recursive Layer tree, each layer containing Boundary shapes and Affector rules that must be evaluated at query time, not just decoded.

FORM PTAT > FORM 0013
  DATA       — dev build path string, irrelevant to rendering
  FORM TGEN > FORM 0000
    FORM SGRP   — shader families (SFAM entries: name, id, weight)
    FORM FGRP   — flora groups
    FORM RGRP   — river groups
    FORM EGRP   — environment groups
    FORM MGRP   — map/fractal groups (MFAM* > MFRC noise generators — confirmed & implemented, see below)
    FORM LYRS > FORM LAYR > FORM 0003   — the actual procedural graph, recursive
      FORM IHDR > ... > DATA   — layer name string
      ADTA       — boundariesFlag / filterFlag / invert flags
      FORM AHCN, ASCN, BCIR, ...  — boundary/affector nodes, one child FORM per rule
      FORM LAYR (nested)   — child layers, arbitrary depth
  FORM 0000       — water map (WMAP) / seed map (SMAP), empty in small test files
Parse dispatch — 4-char FORM tag switch, same pattern as our IFF reader

Core3's Layer::parse (Layer.cpp:36-118, 120-303) reads each subchunk's 4-byte FORM tag and dispatches via switch — 'AHCN'→AffectorHeightConstant, 'BCIR'→BoundaryCircle, etc. — trying boundary, then filter, then affector, then nested child Layer. A Layer owns Vector<Boundary*>, Vector<AffectorProceduralRule*>, Vector<FilterProceduralRule*>, Vector<Layer*> children (Layer.h:22-38) — this maps directly onto FSWGIffReader's existing chunk-walk API, same as every other format we've decoded.

Height evaluation algorithm — confirmed exactly, read directly from source (not summarized)

ProceduralTerrainAppearance::getHeight(x,y) (.cpp:430-457): for each enabled top-level layer independently (they do not chain a shared transform to each other — only nested children do), call processTerrain(layer, x, y, height&, parentTransform=1.0, HEIGHTTYPE), accumulating into one shared height passed by reference. Exact recursive body (.cpp:287-399):

transformValue = 0
if layer has enabled boundaries:
    for each: transformValue = max(transformValue, calculateFeathering(boundary.process(x,y), boundary.FeatheringType))
              if transformValue >= 1: break
else:
    transformValue = 1.0   // no boundaries = unconditional
if layer.bInvertBoundaries: transformValue = 1 - transformValue

if transformValue != 0:
    # (filters: none in MVP scope — can only lower transformValue, invertFilters() applies after)
    for each enabled affector matching requestedType:
        affector.process(x, y, transformValue * parentTransform, height&)
    for each enabled child layer:
        processTerrain(child, x, y, height&, parentTransform * transformValue, requestedType)
return transformValue

Note the two different multiplications: affectors use transformValue * parentTransform (this layer's own gate times everything above it); the recursive call passes parentTransform * transformValue onward as the new accumulated chain for descendants. Same framework serves getEnvironmentID().

calculateFeathering(value, featheringType) — confirmed exact (ProceduralTerrainAppearance.cpp:257-285)
0: passthrough
1: value²
2: sqrt(value)
3: value² × (3 - 2×value)   // smoothstep-like
default: 0
TypeNameWhat it does
Affector (MVP subset)AffectorHeightConstantAdd/subtract/scale/zero/lerp a constant height, blended by the boundary value (AffectorHeightConstant.h:52-76)
AffectorHeightFractalSame operationType blend as above, but height × MapFractal::getNoise(x,y) instead of a flat constant — fully confirmed and implemented (SWGTerrainNoise.h/.cpp): exact port of Core3's Random (Park-Miller LCG + Bays-Durham shuffle), PerlinNoise (2D case), and all 5 MapFractal combination formulas + bias/gain reshaping
AffectorHeightTerraceFlattens height into steps (flatRatio controls flat-vs-slope portion per step) — plateau/terracing effect (AffectorHeightTerrace.h:51-74)

Per-layer bounding box — for area-limited rendering, not just the whole planet

The client only needs to render terrain in a bounded area around the player, not a whole planet at once. Core3 already demonstrates the exact computation needed for a query area — TerrainGenerator::getFullBoundaryCircle() (.cpp:19-91) recursively unions enabled layers'/children's boundary min/max X/Y into one aggregate box (there just for a "whole terrain" bounding circle). Each MVP boundary type already carries what's needed to compute its own box trivially: Circle is center ± radius; Rectangle is min/max(X0,X1)/min/max(Y0,Y1) (not pre-sorted in our reader, unlike Core3's initialize()); Polygon is min/max over Vertices. A per-layer aggregate (own boundaries ∪ enabled children, recursively) lets heightmap baking (step 3 below) skip any layer whose box doesn't overlap the region being baked — a real win, since large planets likely have many small localized layers (individual buildings/POIs) irrelevant outside their own area. One caveat: a layer with zero boundaries always evaluates to 1.0 everywhere and has no finite box — rare (typically global/base layers), so it doesn't undermine the approach.

This MVP subset is not a corner-cut — it's the real coverage

~20 affector types and 5 boundary types exist total, but two boundary types (BoundaryPolyline-adjacent stubs) are confirmed dead code even in the real client. The 3+3 subset above covers height-shaping for the large majority of real terrain; rarer affector types (roads, rivers, procedural rules) can be added later without restructuring the evaluator, same as how .msh's materials were deferred without blocking geometry.

No baked heightmap anywhere — must bake and cache it ourselves

getHeight() has no memoization in Core3 either — every call does a full recursive layer/boundary/affector walk. TerrainMaps (WMAP/SMAP) are just water/seed maps, not a cached heightmap. For a UE terrain grid we'll need to evaluate this per-vertex ourselves and bake the result into a local (gitignored, per-machine) cache, same pattern as the mesh reader's Saved/MeshCache/ — never a pre-baked asset shipped with the project.

Shader/flora — no server-side ground truth

Confirmed gap: Core3 parses this data but never evaluates it

AffectorShaderConstant parses its fields (familyId, feathering) but never overrides process()/isEnabled() — it inherits the base class's no-op. AffectorProceduralRule's type constants (AffectorProceduralRule.h:21-26) only define HEIGHT*/ENVIRONMENT — there's no shader or flora type at all. This makes sense: the server has no reason to render grass or splat textures. But it means we have solid, tested ground truth for height and environment only — texture splatting and flora density/placement will need their meaning inferred from the parsed field layout ourselves (same empirical approach as the .msh vertex-flags decode), or deferred entirely for an initial flat-shaded/no-flora terrain milestone.

ALandscape runtime creation — real risk, chosen anyway

Verified directly against UE 5.8 engine source (Engine/Source/Runtime/Landscape/ vs the editor-only Engine/Source/Editor/LandscapeEditor/) before committing to an approach — same category of concern as skeletal meshes, checked rather than assumed.

Confirmed runtime-safe

ALandscape (Landscape.h:276), ALandscapeProxy (LandscapeProxy.h:450), ULandscapeComponent (LandscapeComponent.h:431) are all unconditionally compiled — spawning the actor itself isn't editor-gated. HeightmapTexture/GetHeightmap() (LandscapeComponent.h:572,810) are plain runtime members — a heightmap UTexture2D can be created and uploaded at runtime via ordinary (non-Landscape-specific) texture APIs.

Confirmed risk — real, not hypothetical
  • UpdateCollisionHeightData — the function that turns a heightmap into landscape collision — is confirmed inside #if WITH_EDITOR (LandscapeComponent.h:1116-1283).
  • ULandscapeHeightfieldCollisionComponent::CollisionHeightData (an FWordBulkData, LandscapeHeightfieldCollisionComponent.h:133) and CreateCollisionObject() (line 309/312) are not editor-gated — runtime code can build the actual Chaos collision object from this bulk data — but nothing runtime-safe computes its contents. We'd have to read UpdateCollisionHeightData's editor-only implementation to understand the exact byte layout it produces, then replicate that computation ourselves and write directly into the field (which is not gated for writes) before calling CreateCollisionObject().
  • ALandscapeProxy extends APartitionActor (World Partition) — whether ad-hoc runtime spawning outside the normal streaming-proxy flow behaves cleanly is unconfirmed, not just untested.
  • No precedent found anywhere in engine source for "create a brand-new landscape and upload brand-new heightmap data the game has never seen, at runtime, in a shipping build."
Decision: attempt real ALandscape, accept the risk

Chosen deliberately over the safer fallback, in order to get native Landscape LOD streaming/collision/tooling if it works. The fallback below is documented as a real contingency, not a hedge — if the collision-data reverse-engineering proves impractical, switching to it doesn't require redoing the format parser or heightmap baking, only the final render/collision step.

Fallback, if the collision-data wall proves real: UDynamicMeshComponent + Chaos::FHeightField

Chaos::FHeightField (Chaos/HeightField.h:41-42) has a plain CHAOS_API constructor taking raw height data directly — confirmed fully runtime-constructible, zero editor gating. Paired with a UDynamicMeshComponent render mesh (the same component family already chosen for regular meshes), this is a fully confirmed-safe path with no unknowns, just without Landscape's native LOD streaming.

Message → visible-in-level: end-to-end integration

The steps above (Parser & render plan) cover the format/algorithm side in isolation. This is the orchestration side — how that pipeline actually gets triggered by network traffic and ends up as terrain the player can stand on, wired into the flow/subsystem architecture already built this session.

The trigger already exists — CmdStartScene.TerrainName

Confirmed directly in our own FCmdStartSceneMessage (CmdStartSceneMessage.h/.cpp): the wire carries an ASCII terrain field, deserialized into TerrainName, right alongside PosX/PosY/PosZ (the player's spawn position — exactly the point terrain needs to be centered on). Per Core3's CmdStartScene.h:28 this is sent as the full virtual path ("terrain/" + zoneName + ".trn") — worth a one-line log confirmation of the live value before relying on it, but not expected to need any transformation. This message is already fully plumbed through FSWGSceneStartPayload into FSWGZoneLoadingState::Enter() — no new message handling needed, just a new consumer of data we already have.

1

New USWGTerrainSubsystem (game instance subsystem)

Same shape as USWGTreSubsystem/USWGObjectGraphSubsystem. Owns the whole pipeline behind one entry point: BeginLoadTerrain(FString TerrainVirtualPath, FVector SpawnPosition). Exposes an OnTerrainReady delegate (broadcast once the region around SpawnPosition has a spawned, collidable landscape) — same pattern as USWGObjectGraphSubsystem::OnZoneLevelRevealed.

Alongside the existing level-load call, add: resolve USWGTerrainSubsystem from the GameInstance (same pattern already used for USWGObjectGraphSubsystem there) and call BeginLoadTerrain(Scene.TerrainName, FVector(Scene.PosX, Scene.PosY, Scene.PosZ)). Compute a cache key from (TerrainVirtualPath, region-around-SpawnPosition) and check Saved/TerrainCache/ before doing anything else. Cache hit → skip straight to step 6 with the cached heightmap grid. Cache miss → continue to step 4.

5

Bake — asynchronous, background thread

Determine the bake region: a box centered on SpawnPosition, sized to a configurable render radius (this is the actual answer to "only render terrain in a certain area" — never the whole planet). Dispatch heightmap evaluation (the ported GetHeight(x,y) per grid vertex, using per-layer bounds culling from step 2 of the render plan) onto a background thread (Async(EAsyncExecution::ThreadPool, ...) or a Task Graph task) — this is the part expensive enough to justify not blocking the game thread, unlike step 4. On completion, write the result to the local cache (step 3) and continue on the game thread.

6

Spawn — ALandscape population, game thread

Spawn/populate the ALandscape for the baked region (render plan steps 5-6): heightmap texture upload, CollisionHeightData population, CreateCollisionObject(). Position it under SpawnPosition. Broadcast OnTerrainReady.

7

Gate the zone reveal on both signals

FSWGZoneLoadingState currently transitions to InWorld as soon as USWGObjectGraphSubsystem::OnZoneLevelRevealed fires (tied to the player's own SceneEndBaselines). Extend this to track both that signal and USWGTerrainSubsystem::OnTerrainReady, transitioning only once both have fired — otherwise the player can be revealed standing over an empty void if terrain baking is still in flight. Order isn't guaranteed either way (object baselines vs. terrain baking could finish first), so this needs to be a two-flag join, not a simple chain.

Explicitly out of scope for this milestone: re-baking as the player moves

This plan gets one region visible around the player's spawn point. As the player walks toward the edge of the baked/spawned area, a real client would need to bake and spawn adjacent regions and unload distant ones — a streaming/chunking scheme. That's a natural, larger follow-up (and would reuse everything here — the reader, evaluator, and baking step are all already region-parameterized), but isn't required to get the "basics" milestone's stationary spawn-in working end to end.
